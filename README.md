# System Assessment

Этот репозиторий используется для архитектурного и технического assessment существующей системы и последующего проектирования целевого решения.

`README.md` является точкой входа для архитектора. Обязательные правила процесса находятся в `ASSESSMENT_PROTOCOL.md`.

## 1. С чего начать

После clone:

1. Прочитать `ASSESSMENT_PROTOCOL.md`.
2. Если проект уже начат, прочитать `00-governance/scope.md` и `00-governance/source-registry.yaml`.
3. Проверить открытые вопросы, предположения и противоречия.
4. Получить исходные документы отдельно и разместить их локально в `sources/`.
5. Если передан `CHAT_HANDOFF.md`, начать с него.
6. Не восстанавливать состояние проекта по истории старых чатов, если есть актуальный repository или handoff.

Для нового проекта initial commit содержит только:

```text
README.md
ASSESSMENT_PROTOCOL.md
.gitignore
```

Структура assessment и проектные реестры создаются в bootstrap-итерации после получения контекста проекта.

## 2. Локальные каталоги

В корне рабочего каталога рекомендуется иметь:

```text
sources/       исходные документы, не Git
deliverables/  собранные DOCX/PPTX, не Git
```

Оба каталога исключены через `.gitignore`.

Исходные документы не являются частью Git repository. В Git хранится их metadata, извлеченные подтверждения и построенная модель.

## 3. Модель работы

Рабочая схема после первого опубликованного assessment snapshot:

```text
PUBLISHED BASELINE
       +
CURRENT WIP
       |
       +-> /questions
       +-> /ideas
       +-> /plan
       +-> /diagram
       +-> /precommit
       |
       v
   /snapshot
       |
       v
CANDIDATE SNAPSHOT
       |
  публикация в Git
       |
   /published
       |
       v
NEW PUBLISHED BASELINE
```

Initial governance commit с `README.md`, `ASSESSMENT_PROTOCOL.md` и `.gitignore` является стартовой точкой процесса, но еще не является опубликованным baseline результатов assessment. Команда `/published` начинает использоваться после первого `/snapshot`.

## 4. Команды

| Команда | Назначение |
|---|---|
| `/questions [scope]` | Показать короткий приоритетный список вопросов, которые полезно решить сейчас |
| `/ideas` | Показать дополнительные идеи AI по текущему этапу без их применения |
| `/plan` | Показать ближайший рекомендуемый план |
| `/diagram [scope] [type] [focus]` | Показать временную sketch-диаграмму текущего понимания |
| `/protocol` | Проверить сам протокол и предложить улучшения без применения |
| `/protocol --fix [proposal-ids]` | Применить выбранные предложения последнего `/protocol` |
| `/precommit` | Проверить проблемы текущего WIP до snapshot/commit |
| `/snapshot` | Собрать полный candidate snapshot repository |
| `/published` | Подтвердить, что последний snapshot опубликован без изменений |
| `/handoff` | Подготовить самодостаточную передачу работы в новый чат |
| `/deliverable` | Показать допустимые итоговые материалы и их готовность |
| `/deliverable <type> <audience> <language> <format> [--visual <style>] [--synthesis <strict|probable>]` | Собрать формальный DOCX/PPTX из published baseline с выбранным visual style и режимом synthesis |

Точная семантика каждой команды определена в `ASSESSMENT_PROTOCOL.md`. `/questions` всегда формирует короткую приоритетную выборку для текущего момента и не является просмотром `questions.yaml`. `/deliverable` без параметров также показывает рекомендуемые visual/synthesis режимы; Mermaid остается инженерным исходником, а не обязательным видом диаграммы в DOCX/PPTX. Для owner-facing AS-IS default synthesis mode - `probable`, чтобы материал восстанавливал наиболее вероятные связи между опубликованными знаниями без превращения их в canonical FACT. Для developer-facing AS-IS default - `strict`.

## 5. Типичная итерация

Для нового источника или логически связанного семейства источников:

1. Передать источник AI или открыть его архитектору.
2. Выполнить предварительную проверку: версия, семейство, дата, актуальность, чувствительные данные, тип источника.
3. Извлечь значимые подтверждения и обновить общую AS-IS модель.
4. Сверить новые сведения с уже известными фактами, предположениями и противоречиями.
5. При необходимости нормализовать API, XML-контракты или физическую модель данных.
6. Обновить проблемы, риски, рекомендации и backlog V2, если текущая стадия assessment и evidence дают для этого достаточное основание.
7. Обсудить спорные места.
8. При необходимости использовать `/questions`, `/ideas`, `/diagram` и `/precommit`.
9. Когда итерация согласована, выполнить `/snapshot`.
10. Опубликовать snapshot в Git и затем сообщить `/published`.

Главная единица прогресса - изменение единой модели системы, а не отдельный summary каждого документа.

## 6. Git

Рекомендуемый initial commit:

```text
bootstrap: добавлен протокол ведения assessment
```

Дальнейшие commit messages используют фиксированный технический префикс и русское описание:

```text
source: обработана функциональная спецификация
model: уточнена модель интеграций
assessment: консолидированы проблемы и риски API
tobe: добавлена возможность самостоятельного управления интеграциями
adr: определена стратегия версионирования API
docs: обновлено описание архитектуры
fix: исправлена интерпретация роли компонента
```

Обычная итерация по source/source family должна по возможности давать один целостный commit, а не множество commits по отдельным facts и findings.

## 7. Продолжение другим архитектором

Другой архитектор должен иметь возможность продолжить проект без истории предыдущего чата.

Минимальный порядок:

1. Clone repository.
2. Прочитать `README.md` и `ASSESSMENT_PROTOCOL.md`.
3. Ознакомиться со scope, source registry и текущей AS-IS моделью.
4. Проверить открытые questions, assumptions и contradictions.
5. Получить необходимые raw sources отдельно.
6. Прочитать `CHAT_HANDOFF.md`, если он передан.
7. Продолжать от актуального Git состояния, не создавая параллельную модель знаний.

Если архитектор вручную изменяет canonical files, следующий AI-сеанс должен получить фактическое актуальное состояние repository. Нельзя сообщать `/published` для snapshot, который был вручную изменен и не показан AI.

## 8. Переход в новый чат

Предпочтительный способ - `/handoff`.

Handoff содержит актуальный repository и `CHAT_HANDOFF.md` с текущей фазой, baseline, WIP, открытыми вопросами, важными решениями и ближайшим следующим действием. `CHAT_HANDOFF.md` не входит в Git repository и в handoff-архиве располагается рядом с каталогом `assessment/`, а не внутри него:

```text
assessment-handoff-...zip
├── CHAT_HANDOFF.md
└── assessment/
    └── ... repository files ...
```

Raw sources по умолчанию в handoff не включаются.

Минимальное сообщение новому AI-чату:

```text
Мы продолжаем system assessment.

Сначала прочитай README.md, ASSESSMENT_PROTOCOL.md и CHAT_HANDOFF.md, если он есть.
Считай переданный repository фактическим текущим состоянием проекта.
Рабочее общение ведем на русском по правилам repository.
Не начинай итоговые документы без команды /deliverable.
Продолжай с шага, указанного в handoff или scope.md.
```

## 9. Итоговые материалы

Основные итоговые форматы:

```text
DOCX  формальные документы
PPTX  презентации и препродажные материалы
```

PDF процесс не формирует. При необходимости пользователь создает PDF отдельно после дополнительного оформления.

Команда `/deliverable` без параметров показывает доступную матрицу типов, аудиторий, языков, форматов, visual styles и synthesis modes, рекомендуемые комбинации и готовность материалов на текущем baseline. Mermaid остается инженерным исходником; итоговые диаграммы формируются как presentation-quality визуализации.

Ключевые правила formal deliverables:

- выбранный `language` действует на весь материал; для `en` narrative, headings, captions и diagram labels должны быть английскими, кроме неизменяемых technical/system names и source literals;
- owner-facing материал должен объяснять связную систему и end-to-end flows, а не экспортировать facts по domains;
- owner-facing AS-IS по умолчанию использует `--synthesis probable`, developer-facing AS-IS - `--synthesis strict`;
- internal assessment IDs не используются как основной язык owner-facing текста; вместо них дается понятное объяснение;
- `sketch` должен проходить layout/readability QA без наложения текста и clipping;
- перед выдачей DOCX/PPTX выполняется post-render QA всего материала.

Базовый английский пример:

```text
/deliverable as-is owner en docx --visual sketch --synthesis probable
```
