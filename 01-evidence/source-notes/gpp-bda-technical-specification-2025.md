# SRC-BDA-002 - техническая спецификация BDA, версия 0.0.2

## Предварительная оценка источника

- Источник: `SRC-BDA-002`.
- Название документа: `BDA Message Detailed Specifications`.
- Версия: `0.0.2`.
- Дата: `02.04.2025`.
- Авторитетность: внутренняя техническая спецификация.
- Временная применимость: `current-at-source-date`.
- Назначение: REST API и структуры базы данных для BDA.
- Связь с `SRC-BDA-001`: технический слой той же функциональной области управления операционным днем.

История версии 0.0.2 отдельно указывает добавление поля `days`, возможность менять порядок процессов в операционном дне, добавление MX-процессов и сортировки в мониторинге.

## Защита чувствительных примеров

В исходном документе присутствуют значения, похожие на реальные секреты и внутренние эксплуатационные данные:

- JWT;
- команда запуска с учетными данными;
- внутренние сетевые адреса и URL;
- технические примеры содержимого сообщений.

Эти значения **не переносятся** в репозиторий, заметки по источнику и реконструированные контракты. В `openapi.yaml` используются только безопасные заполнители `<REDACTED_JWT>`, `<REDACTED_COMMAND>`, `<REDACTED_INTERNAL_URL>`. Сам факт наличия чувствительных примеров сохранен как `EV-BDA-026`.

## REST API

Обзор спецификации содержит 39 операций. Они относятся к семи группам:

- шаблоны (`templates`);
- определения процессов (`periods`);
- операционные дни (`operation-days`);
- архив (`archives`);
- аутентификация и пользователь;
- процессы конкретного операционного дня (`operation-period`);
- мониторинг (`monitoring-menus`).

Нормализованный контракт: `02-as-is/normalized/rest/bda-api/openapi.yaml`, идентификатор `NORM-REST-001`.

### Правило реконструкции

В OpenAPI перенесены документированные HTTP-методы, пути, параметры путей, модели ответов и коды HTTP. Неописанные детали не достраиваются как `FACT`:

- тела изменяющих запросов в основном оставлены как `documentation-gap`;
- для входа тело JSON-запроса введено только как явный `INFERENCE` из `username/password` и `Content-Type: application/json`;
- схема тела ошибки не выдумывается;
- формат и тип содержимого ответов операций экспорта остаются `UNKNOWN`;
- расположение некоторых параметров операций экспорта остается `UNKNOWN`;
- реальный адрес хоста заменен нейтральным заполнителем.

### Несогласованности путей

Зафиксированы два конфликта уровня контракта.

`CONTR-BDA-001`: обзор определяет получение списка шаблонов как `GET /api/v1/templates`, но детальный раздел 2.1 указывает путь параметров процесса. В реконструкции выбран `/api/v1/templates`, поскольку он согласуется с названием операции и не дублирует 2.2.

`CONTR-BDA-002`: получение данных процессов операционного дня имеет два разных пути - вариант обзора через `operation-period` и вариант детального раздела 2.28 через `period-details`. В реконструированном OpenAPI выбран путь детального раздела; альтернативный путь сохранен как конфликт источника.

## Модели API

Источник именует 15 моделей:

`Template`, `Period`, `Parameter`, `OperationDay`, `Archive`, `ArchiveOperationPeriod`, `Login`, `Authority`, `OperationPeriod`, `XohksCalculation`, `SuccessXohks`, `StatusAndPrice`, `FindMonitoringInfos`, `FailedXohks`, `MtFileMonitoring`.

Для нормализации добавлены вспомогательные схемы `ParameterValue`, `ParameterSet`, `LoginRequest`, `Username`, `StartProcessResult`.

Внутренние расхождения не скрываются:

- `Parameter` одновременно показан как оболочка и как набор полей отдельного параметра (`CONTR-BDA-003`);
- `OperationPeriod` расходится между примерами JSON и таблицей полей по `periodName/templateName` против `periodNames/templateNames`, а также по типу `operationDayName` (`CONTR-BDA-004`);
- в моделях мониторинга есть несколько расхождений между примерами и таблицами типов/полей;
- `Parameter.days` документирован на уровне API, но не имеет физической колонки в `BDA.PARAMETERS` (`CONTR-BDA-005`).

Реестр моделей и связей с БД: `02-as-is/normalized/rest/bda-api/api-models.yaml`.

## Физическая база данных BDA

Источник определяет две схемы.

### `BDA`

- `OPERATION_DAY`;
- `OPERATION_PROCESS`;
- `PARAMETERS`;
- `PROCESS`;
- `TEMPLATE`;
- `TEMPLATE_PROCESS`;
- `USERS`;
- `AUTHORITY`;
- `USER_AUTHORITIES`.

### `BDA_ARCHIVE`

- `OPERATION_DAY`;
- `OPERATION_PROCESS`.

Нормализованная модель: `02-as-is/normalized/data/bda-db.yaml`.

Источник описывает семантику идентификаторов и ссылок, но не публикует ограничения DDL. Поэтому `ID` не повышается автоматически до физического PK, а смысловые связи хранятся в `logical-foreign-keys.yaml` как логические ссылки с `physical_constraint_status: unverified`.

Особенность `BDA.PARAMETERS`: `REFERENCE_ID` полиморфен и интерпретируется по `TYPE = PERIOD | TEMPLATE | OPERATION_DAY`. Это прямо подтверждает хранение параметров в трех контекстах, но не означает наличие одного физического FK.

## Аутентификация и ошибки

Подтверждено:

- вход по `username/password`;
- успешный вход возвращает JWT и `authorities`;
- `BDA.USERS.PASSWORD` должен храниться как bcrypt-хэш;
- большинство разделов API перечисляют `400` и `401`;
- `404` явно указан только в детальном разделе 2.1.

Не подтверждено:

- точный заголовок `Authorization` или схема `Bearer`;
- управление ключами подписи;
- срок действия, обновление, отзыв и выход;
- MFA/SSO;
- единый формат тела ошибки;
- семантика `403`/`5xx`.

В OpenAPI HTTP Bearer указан только как помеченный `INFERENCE`; вопрос остается в `Q-BDA-003`.

## Сквозная проверка

Проверяется цепочка:

`User workflow -> Capability -> REST operation -> API model -> Physical DB object`.

Названия уровней в этой строке сохранены как технические термины модели. Результат проверки:

- определения процессов - полный путь до `BDA.PROCESS`/`BDA.PARAMETERS`;
- управление шаблонами - полный путь до `BDA.TEMPLATE`, `BDA.TEMPLATE_PROCESS`, `BDA.PROCESS`, `BDA.PARAMETERS`;
- жизненный цикл операционного дня - путь до `BDA.OPERATION_DAY`;
- выполнение процессов дня - путь до `BDA.OPERATION_PROCESS`/`BDA.PARAMETERS`, но точный механизм исполнения команд остается `UNKNOWN`;
- архив - путь до `BDA_ARCHIVE.OPERATION_DAY`/`OPERATION_PROCESS`, но физическое хранение экспортируемого XML-артефакта не документировано;
- мониторинг - путь подтвержден до REST и моделей API, но поставщик данных физической БД не указан и остается `documentation-gap/UNKNOWN`;
- аутентификация (`CAP-ASIS-020`) - путь до `BDA.USERS`/`AUTHORITY`/`USER_AUTHORITIES`, но транспорт и жизненный цикл JWT остаются `UNKNOWN`.

Отсутствие физического звена не считается автоматически дефектом системы: если источник не дает достаточного подтверждения, это фиксируется как пробел документации или `UNKNOWN`.

Каноническая межслойная модель: `02-as-is/bda-cross-layer-model.yaml`.
